## 1. Summary

Jarvis Mission Control is a **single-user web dashboard** that visualizes an existing,
fully-built job-application pipeline (job discovery → AI evaluation → tailored resume →
cover letter → apply session → tracker → email reply-matching) that runs locally on my
Mac and writes structured data files. The pipeline already works; what's missing is
**sight**: a ranked review queue, a pipeline board, funnel analytics, a follow-up
queue, and an intern-recruiting-season calendar — instead of markdown tables in a
terminal.

**Core doctrine (non-negotiable):** the Mac's files are the single source of truth.
This app **ingests** snapshots pushed from the Mac and **never writes back
automatically**. Any edit made in the dashboard (status change, note, follow-up done)
is queued as a *pending change* and rendered as a copy-pasteable CLI command
(`python3.11 scripts/track.py set 7 responded --date 2026-08-02 --note "..."`) that I
run on the Mac myself. The dashboard suggests; the human applies. Nothing in this app
ever auto-submits an application, sends an email, or logs into any job board.

## 2. Problem statement

I am a UC Berkeley CS/DS student applying to US SWE internships at volume
(target: 25+ tracked applications during the Aug–Oct 2026 recruiting season). My
pipeline automates the hard parts, but its outputs live in markdown/TSV files:

- The **discovery queue** (150+ scored listings) is a markdown table — no way to scan,
  filter, or mark-reviewed quickly.
- The **tracker** funnel/status data has no visual: no board, no conversion rates at a
  glance, no "what needs my attention today."
- **Follow-ups due**, **blockers found by pre-scan**, and **email-reply suggestions**
  are separate CLI outputs — there is no single morning view of "what do I do next."
- Which **resume version / letter tone** went to which company (the data exists) has
  no comparative view, so I can't see what's working once responses arrive.

Time cost aside, the real risk is *tracker death*: friction at the moment of least
motivation. A dashboard I open once a day fixes that.

## 3. Goals

1. One morning view: today's follow-ups, pending email suggestions, top queue items,
   blockers — in under 5 seconds of scanning.
2. Review the discovery queue at 10× current speed (sort/filter/keyboard, score
   badges with reasons).
3. See the funnel with per-stage conversion and score-band splits, honestly
   right-censored ("n still in flight").
4. Never let a follow-up or application deadline slip during the Aug–Oct season.
5. Zero risk to the pipeline: read-mostly by construction; export-commands for writes.

### Non-goals (v1 — do NOT build these)

- No auto-apply, no scraping, no logging into job boards, no browser automation.
- No LLM calls in the app (all scores/analysis are precomputed upstream; do not add
  AI features, chatbots, or "AI insights").
- No resume/letter *generation* (exists upstream).
- No multi-user support, no teams, no sharing, no public pages.
- No email sending of any kind.
- No mobile app (responsive web is enough).

## 4. Target user

Exactly one: me. Skill level: I read code but want a polished, fast UI. I will use
this daily on desktop Chrome, occasionally on phone.

## 5. Data model — THIS IS THE CONTRACT, paste-accurate

The Mac pushes a JSON snapshot (schema below). Store snapshots and normalize into
these tables. **Field names must match exactly** — the Mac-side push script is already
specified against them. All dates are ISO `YYYY-MM-DD` strings.

```
IngestSnapshot            # one per push, keep last 30 for history/diff
 - id, received_at, payload_version (int, currently 1), raw_json

Application               # from tracker rows
 - num (int, UNIQUE — the pipeline's row id; NEVER renumber)
 - date, company, role, score (string: "4.1" | "N/A" | ""), status
   (evaluated|applied|oa|responded|interview|offer|hired|rejected|discarded|withdrawn)
 - contact, via, resume, letter, report, notes (all strings, may be "")

StatusEvent               # from status_log.tsv (append-only upstream)
 - num (int), date, from_status, to_status, source (cli|sync|correction|followup|round), note

QueueItem                 # from discovery queue
 - rank (int), score (float), company, title, posted (date string), url
 - reviewed (bool, LOCAL to the app — survives re-ingest by url match)

EvalSummary               # from eval reports' machine summaries
 - num (int), url, company, role, score, recommendation, legitimacy,
   blockers (string[], may be empty), warnings (string[])

CoverLetter               # from covers ledger
 - num (int), file, date, tone, gate_clear (bool)

FollowupItem              # computed upstream, pushed as-is
 - num (int), company, role, urgency (urgent|overdue|needs-data|waiting|cold),
   next_date, reason

ReplySuggestion           # from email reply-matching digests
 - message_date, subject, from_addr, kind, confidence, suggested_command (string),
   blocker (string, "" if actionable)

PendingChange             # created IN the app by me; the write-back queue
 - id, created_at, num (int), kind (status|note|followup_done|contact)
 - payload (json), command (string — the exact CLI command to run on the Mac)
 - state (pending|copied|applied|dismissed)

SeasonDeadline            # manual entries + optional CSV import
 - id, company, program, opens_date, closes_date, url, notes, source (manual|import)
```

Ingest rules — per-table semantics (these ARE the idempotency contract):

- `applications` / `evals`: upsert by `num`.
- `queue`: upsert by `url`, ALWAYS preserving the local `reviewed` flag.
- `status_events`: append-only, dedup'd on all fields.
- `covers`: upsert by (`num`, `file`).
- `followups` and `reply_suggestions` are **computed snapshots**: whenever the key is
  present in the payload (even as `[]`), REPLACE that table's contents entirely —
  these two tables are exempt from the never-delete rule (a follow-up completed on
  the Mac must disappear here on the next push).
- A field missing from a snapshot = keep the existing value; an application absent
  from a snapshot = keep it (snapshots may be partial). NEVER delete rows on ingest
  for `applications`, `queue`, `evals`, `covers`, `status_events`.
- Store each payload's `generated_at`; header staleness (F1) is measured from the
  latest snapshot's `received_at`.

One intentional quirk in the example above: `applications[0].letter` says
`...cover-v4.md` while `covers[0].file` says `...cover-v6.md` — this is REAL data,
not an error (the ledger tracks the latest letter version). Join covers to
applications by `num`, never by filename. Do not "fix" the seed data.

## 7. Design requirements

- **Look:** clean mission-control aesthetic — dark mode default with light toggle,
  dense but readable tables, generous Today view. Sans-serif, no marketing-page
  styling; this is an operator console. Use shadcn/ui components + Tailwind.
- Score badges: red <3.0, amber 3.0–3.9, green ≥4.0 (matches my pipeline's 4.0 gate).
- Urgency chips: urgent=red, overdue=orange, needs-data=purple, waiting=gray, cold=blue.
- All timestamps display in America/Los_Angeles — and ALL date computations
  ("today", follow-up due, >48h staleness, the 21-day ghost flag, >60d stale
  postings, ISO-week membership for the weekly goal, and the `{today}` substituted
  into pending-change commands) use the current date in America/Los_Angeles,
  regardless of server timezone (Replit servers run UTC).
- Snappy: any view interactive in <1s after load with 500 queue items / 100
  applications; paginate or virtualize past 200 rows.
- Every destructive UI action (dismiss pending change, delete deadline) needs an
  undo toast, not a confirm dialog.
- Empty/error states are first-class: never render a blank panel; say what's missing
  and which pipeline command produces it.

- **Security check before finishing:** no route accessible logged-out except ingest

- **Final review pass:** re-read §1 doctrine and §3 non-goals, then grep the codebase

## 12. Risks & mitigations

- **Two sources of truth drift** → mitigated by doctrine (§1): ingest-only writes,
  pending-change tray, "not yet synced" badges, staleness warning.
- **Replit agent inventing data or features** → seed ONLY from §5 example; §3
  non-goals are hard constraints; final review pass greps for violations.
- **Credit burn** → build in Economy/default mode; no LLM integrations; app compute
  is a small always-cheap web service.
- **Schema drift vs the Mac push script** → `payload_version` field; reject unknown
  major versions with a clear error rather than guessing.
- **Security of the ingest endpoint** → long random token, rate limit, size cap,
  no reflection of payload contents into HTML without escaping.

## 14. Portability requirements (self-host later — these are hard requirements NOW)

This app will eventually move to my own Linux VPS. Build so that migration is
config-only, never surgery:

1. **Everything is code in the repo.** No logic may live only in Replit UI settings.
   The GitHub repo must contain the complete, runnable application.
2. **Standard runtime:** the app must start with `npm install && npm run build &&
   npm start` given only env vars (`DATABASE_URL`, `INGEST_TOKEN`, `AUTH_MODE`,
   `OWNER_USER_ID`, `SESSION_SECRET`, `AUTH_BASIC_USER`, `AUTH_BASIC_PASSWORD_HASH`,
   `PORT`). No Replit-only APIs, SDKs, or file paths anywhere outside the two seams
   below.
3. **DB seam:** all database access through `DATABASE_URL` + standard Postgres
   client/ORM. Migration to any Postgres = `pg_dump` → restore → repoint the URL.
   Never use Replit Key-Value/Object storage.
4. **Auth seam:** one middleware module (`server/auth.ts` or equivalent) is the ONLY
   place that knows about Replit Auth. `AUTH_MODE=replit` (default on Replit; owner
   check via `OWNER_USER_ID`) | `AUTH_MODE=basic` (single user from
   `AUTH_BASIC_USER` + `AUTH_BASIC_PASSWORD_HASH` (bcrypt), for the VPS). Both modes
   produce the same `req.user` shape. Write a test that boots the app in-process
   with `AUTH_MODE=basic` and the two env vars set, and exercises login + a
   protected route + a wrong-password 401 — this runs inside Replit's normal test
   suite and proves the seam works before I ever need it.
5. **`MIGRATION.md` in the repo root:** exact self-host steps — env vars table,
   `pg_dump`/restore commands, `AUTH_MODE=basic` setup, reverse-proxy note (app
   binds `0.0.0.0:$PORT`), and anything Replit-specific someone would need to know
   to leave Replit. Keep it current as you build.
